Swarajya PRO — Provisioning API

Machine-to-machine endpoint to create a customer account and mint MCP access URL(s) right after a successful payment. One call in, ready-to-share connector URLs out.

Before you integrate: the endpoint must be live on mcp.swarajyamag.com and the bearer token (PROVISION_API_KEY) must be set on the server. The Swarajya team will share that token with you separately and securely — it is not in this document.

Authentication

Send a bearer token in the Authorization header. This token is server-to-server only — never expose it in a browser / frontend / mobile app. Call this endpoint from your backend (e.g. inside your payment-success webhook handler).

Authorization: Bearer <PROVISION_API_KEY>

Endpoint

POST https://mcp.swarajyamag.com/provision/groups

Content-Type: application/json

Request body

FieldTypeRequiredDescription
groupstringyes*Customer / organisation name (e.g. "Varahe Analytics"). Creates a new account. *Required unless group_id is given.
group_idstringnoProvide an existing group's id to add seats to it (renewal / seat top-up) instead of creating a new account. Use one of group OR group_id.
seatsintegernoHow many connector URLs to mint (1–500). Default 1. Each URL is one seat.
contact_emailstringnoBilling / admin contact for the account.
labelstringnoNames the seat(s) for your own tracking. With multiple seats it becomes label #1, label #2, …
monthly_request_quotaintegernoMax MCP requests/calendar-month for the whole account (shared across its seats). Omit to use the server default (250). Send a higher number for PRO teams (e.g. 5000).
rate_limit_per_minuteintegernoBurst limit per minute (shared). Omit to use the server default (20).
expires_in_daysintegernoAccess expiry, e.g. 365 for an annual plan. Omit for no expiry.

Example request

cURL

curl -X POST https://mcp.swarajyamag.com/provision/groups \
  -H "Authorization: Bearer $PROVISION_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
        "group": "Varahe Analytics",
        "contact_email": "ops@varahe.com",
        "seats": 10,
        "monthly_request_quota": 5000,
        "expires_in_days": 365
      }'

Node.js (fetch)

const res = await fetch("https://mcp.swarajyamag.com/provision/groups", {
  method: "POST",
  headers: {
    "Authorization": `Bearer ${process.env.PROVISION_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    group: "Varahe Analytics",
    contact_email: "ops@varahe.com",
    seats: 10,
    monthly_request_quota: 5000,
    expires_in_days: 365,
  }),
});

if (!res.ok) throw new Error(`provision failed: ${res.status}`);
const data = await res.json();
// data.access_urls -> email these to the customer
// data.group_id    -> STORE against the customer (needed for renewals / add-seats)

FieldMeaning
group_idStore this against the customer. Pass it back as group_id to add seats or renew later.
access_urls[]One connector URL per seat. These are the credentials — email them to the customer (see "What the customer does" below).
access_urlConvenience: the first URL in the list.
created_grouptrue when a new account was created; false when seats were added to an existing group_id.

Error responses

StatusBodyCause
401{"detail":"invalid or missing bearer token"}Missing/wrong Authorization header.
404{"detail":"group_id not found"}A group_id was passed but doesn't exist.
422{"detail":"provide `group` (name) or `group_id`"}Neither group nor group_id supplied (or a field failed validation).
503{"detail":"provisioning disabled: set PROVISION_API_KEY"}The webhook isn't enabled on the server yet.

Suggested integration flow

  1. Your payment-success webhook (Razorpay/Stripe/etc.) fires on a captured payment.
  2. Your backend derives seats from the plan purchased and calls POST /provision/groups.
  3. Store the returned group_id against the customer/order in your DB.
  4. Email the access_urls to the customer with setup instructions.
  5. For renewals or extra seats later, call again with group_id (not group).
Idempotency — important. Each call with group creates a new account. Payment webhooks are retried by the provider, so guard against double-provisioning on your side: dedupe on the payment/order id (e.g. only provision once per order_id), and store the resulting group_id. There is no server-side idempotency key today.

What the customer does with an access URL

Each access_url is an MCP connector URL. The end user adds it as a custom connector in their AI client — Claude (Desktop / web / Code), ChatGPT, or Gemini — and their assistant can then search and cite Swarajya's archive. No install or API key on their side; the URL is the credential, so it should be treated as a secret.
